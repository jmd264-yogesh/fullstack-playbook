# Role Path: Software Engineer

**Level:** 🟡 Intermediate - assumes basic technical/business context

## Why you need this playbook

You know how to code. What this playbook standardizes is how work moves through this organization specifically - the delivery process, the stack-specific conventions, and the discipline of checking a request against real business need before building it, so you don't ship the wrong thing well.

## Reading list

1. [Choosing the Right Solution](/business-foundations/choosing-the-right-solution) - the framework for sanity-checking a request before you commit to an approach.
2. [Application vs Automation](/business-foundations/application-vs-automation) and [Application vs Integration](/business-foundations/application-vs-integration) - the two comparisons that come up most often day-to-day.
3. [Delivery Lifecycle Overview](/delivery-lifecycle/overview) - the phases your work moves through.
4. [Requirement Intake](/delivery-lifecycle/requirement-intake) - how requirements arrive, in various states of completeness.
5. [Solution Design](/delivery-lifecycle/design-phase) - how a chosen approach becomes a concrete design before coding starts.
6. [Development & Coding Standards Overview](/coding-standards/overview) - then drill into the specific frontend/backend/database pages for your stack.
7. [Project Setup Guide](/coding-standards/project-setup) - how new projects here are scaffolded.
8. [Testing Strategy](/security/testing/overview) - unit, integration, and E2E expectations.
9. [CI/CD Pipeline](/coding-standards/ci-cd) - how your code gets validated and shipped.
10. [Security Guardrails](/security/security-guardrails) and [General Security Checklist](/security/security-checklist) - what's expected of you before code is considered secure.
11. [Agile Board Standards](/delivery-lifecycle/agile-board-standards) - how work is tracked and estimated here.
12. [Quality Gates Overview](/quality-gates/overview) - what has to be true before something is considered done.

## You'll know you're ready when you can answer

::: info Ready check
- What questions do you ask before accepting a ticket's stated solution at face value?
- What's the review and CI process a pull request goes through here before merge?
- What's the minimum testing expectation for a change in your part of the stack?
- Where do you go to check the security and coding standards for your specific framework?
:::
