## Containers & Docker Basics

"It works on my machine" is the problem containers solve. A **container** packages an application together with everything it needs to run (runtime, libraries, config) so it behaves identically on a laptop, in CI, and in production.

## Image vs container

| Term | Plain-English meaning |
|---|---|
| **Dockerfile** | A text recipe describing how to build an image (base OS, install dependencies, copy code, how to start the app) |
| **Image** | The built, immutable artifact produced from a Dockerfile — like a class in OOP terms |
| **Container** | A running instance of an image — like an object instantiated from that class |
| **Registry** | Where built images are stored and pulled from (e.g. Docker Hub, a private registry) |

## A minimal Dockerfile, explained line by line

```dockerfile
FROM node:20-alpine AS builder      # start from a small base image with Node pre-installed
WORKDIR /app
COPY package*.json ./               # copy only manifest files first...
RUN npm ci                          # ...so this expensive step is cached unless dependencies change
COPY . .
RUN npm run build

FROM node:20-alpine                 # a fresh, smaller final image (multi-stage build)
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
EXPOSE 3000
CMD ["node", "dist/main.js"]
```

The two-stage structure matters: the `builder` stage has all the build tooling (TypeScript compiler, dev dependencies), but the **final image only contains the compiled output** — smaller, faster to deploy, and with a smaller attack surface. This is exactly the pattern required in [Coding Standards: Docker](/coding-standards/infrastructure/docker).

## Everyday commands

| Command | What it does |
|---|---|
| `docker build -t myapp:latest .` | Build an image from the Dockerfile in the current directory |
| `docker run -p 3000:3000 myapp:latest` | Run a container from that image, mapping port 3000 |
| `docker ps` | List running containers |
| `docker logs -f <container>` | Stream a container's logs |
| `docker compose up` | Start every service defined in `docker-compose.yml` together |

## Running the whole stack locally with Compose

Most local setups here start with one command (see [Developer Experience](/engineering/developer-experience)):

```yaml
# docker-compose.yml
services:
  api:
    build: .
    ports: ["3000:3000"]
    environment:
      DATABASE_URL: postgres://postgres:postgres@db:5432/app
    depends_on: [db]
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: postgres
    ports: ["5432:5432"]
```

Running `docker compose up` starts the API and a real Postgres database together, networked so `db` resolves by name — no manual local Postgres install required.

## Why containers, specifically

- **Consistency**: the same image that passed tests in CI is the exact artifact deployed to production — no "rebuilt from source on the server" drift.
- **Isolation**: each container has its own filesystem and process space, so dependency versions between services never clash.
- **Fast, cheap scaling**: starting another container is much faster than provisioning another full server, which is what lets Kubernetes do [rolling updates and canary deployments](/coding-standards/ci-cd).
