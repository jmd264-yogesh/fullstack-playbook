## Transformation Orchestration: The Tooling Matrix

We have chosen SQL as our language for 80% of transformation workload. Now we must choose the vessel to
deliver it. We compare the three most common execution frameworks:
* dbt Core
* Notebooks (PySpark/PySQL)
* Stored Procedures

We have established that SQL is our preferred transformation language. But SQL
files sitting in a folder are not a platform - they are a liability. We
need a framework to compile, test, and deploy that SQL safely.

### dbt is the "Terraform" for Data Transformation
Just as Terraform became the industry standard for Infrastructure as Code (IaC) by abstracting away the complexities of AWS, Azure, and GCP, dbt has become the standard for Transformation as Code.

While modern data platforms (Snowflake, Databricks, BigQuery) offer built-in transformation tools, relying on them creates technical debt and vendor lock-in. dbt solves this by decoupling the business logic from the execution engine. It significantly reduces coupling to a specific execution engine by standardising transformation logic, while still allowing engine-specific optimisations when needed

We prefer **dbt** as the JMAN standard for three critical reasons:

**Productivity** In traditional Stored Procedures, an engineer spends
40% of their time writing \"Plumbing Code\" (CREATE TABLE, DROP TABLE,
MERGE INTO). dbt abstracts this away entirely. Our engineers write
simple SELECT statements, and dbt handles the materialization (Table vs.
View vs. Incremental) automatically. This allows us to **deliver
features faster**.

**Enforcing the \"JMAN Standard\" (Naming)** One of the most complex
parts of scaling a team to 700 people is getting everyone to name things
the same way. dbt solves this architecturally.

-   **Configuration over Discipline:** We configure naming patterns in
    the dbt\_project.yml file.
-   **File-Based Identity:** The file name dictates the database object
    name. A developer cannot accidentally name a table
    Customer\_Final\_V2 if the file is named dim\_customer.sql. The tool
    enforces the standard for us.

**Automated Quality (CI/CD)** dbt allows us to validate quality *before*
code is merged.

-   **Linting:** We use SQLFluff in our pipeline to automatically check
    that every SQL line follows JMAN\'s formatting standards.
-   **Testing:** We run automated tests on every Pull Request. If a
    developer breaks a naming convention or introduces a duplicate
    primary key, the **pipeline fails immediately**. This prevents \"bad
    code\" from ever reaching the production environment.

### Performance impact

A common misconception is that dbt is slower than Spark because it generates text-based SQL. In reality, dbt
leverages **Push-Down optimisation**. It compiles your logic into highly
optimised SQL that runs directly on the Warehouse\'s MPP engine (e.g.,
Databricks Photon or Snowflake).

For 90% of high-volume transformation use cases (Joins, Aggregations),
this architecture is **more performant and cost-efficient** than
spinning up separate Spark clusters, as it avoids the overhead of data
serialisation and network transfer. We reserve Notebooks only for
workloads where SQL execution plans hit their architectural limits
(e.g., complex iterative algorithms).

We use **Notebooks** for Data Science and ingestion. We
use **SQL** for Transformation. We use **dbt** to govern, test, and
document that SQL.
