## Databases

<Callout type="warning">
  **Production Impact is Real** - A poorly written extract can lock tables, spike CPU, and degrade the production application. Always understand the source system's workload profile before running any query.
</Callout>

### What this covers

PostgreSQL, SQL Server, MySQL, Oracle, Azure SQL, Amazon RDS, and any relational database serving a transactional application.

### Characteristics

| Characteristic | Detail |
|----------------|--------|
| **Access method** | JDBC/ODBC, read replicas, CDC (WAL/binlog/redo log), database-native export (COPY, BCP) |
| **Schema control** | Shared with application team - migrations can change schema without warning |
| **Concurrency** | Analytical queries compete with transactional workloads unless isolated |
| **Change detection** | CDC (best), `updated_at` columns (common), increasing ID (inserts only) |
| **Delete handling** | Hard deletes are invisible without CDC - records simply disappear |
| **Data types** | Rich type system - `MONEY`, `JSONB`, `GEOMETRY`, `ARRAY` require careful mapping |

### Common Pain Points

| Pain Point | Description | Example |
|---|---|---|
| **Source system impact** | Analytical queries compete with transactional workloads, causing application slowdowns. | 30-minute full extract against production PostgreSQL caused the web application to timeout during peak hours. |
| **CDC configuration complexity** | Log-based CDC requires database-level settings, often needing DBA and a restart. | PostgreSQL: `wal_level = logical` requires restart. SQL Server: CDC enabled per table. Oracle: supplemental logging + LogMiner. |
| **Replication slot management** | CDC state must be managed. Abandoned slots cause disk bloat. | Postgres replication slot unconsumed for 3 days. WAL files grew to 200GB. Disk full, production outage. |
| **Schema migration conflicts** | Application deployments change schema. CDC pipeline breaks if it doesn't handle evolution. | App added `NOT NULL` column. CDC pipeline received rows with new column but target didn't have it. Ingestion failed. |
| **Data type mismatches** | Database types don't map cleanly to target platform types. | SQL Server `MONEY` extracted as string. Oracle `NUMBER(38,0)` overflows `INT`. PostgreSQL `JSONB` loses structure. |
| **Network and firewall** | Production databases are behind firewalls, VPNs, or private networks. | Self-hosted SQL Server on-premises required VPN tunnel + firewall rule change. Two-week lead time from client IT. |

### CDC Configuration by Database

<Callout type="info">
  **CDC is the Gold Standard for Databases** - Log-based CDC captures inserts, updates, and deletes with minimal source impact. It should be your default strategy for any production database.
</Callout>

| Database | CDC Method | Setup Requirement | Restart? | Key Gotcha |
|----------|-----------|-------------------|----------|------------|
| **PostgreSQL** | Logical replication (WAL) | `wal_level = logical` | Yes | Replication slots grow unbounded if consumer stops |
| **SQL Server** | Change Tracking or CDC tables | Enable per database + per table | No | CDC cleanup job must be configured or log grows |
| **MySQL** | Binary log (binlog) | `binlog_format = ROW` | Yes | `binlog_row_image = full` required for all columns |
| **Oracle** | LogMiner / GoldenGate | Supplemental logging enabled | No | LogMiner is slow on large redo logs; GoldenGate is licensed |
| **Azure SQL** | Change Tracking | Enable per database + per table | No | Only tracks which rows changed, not old values |

### Platform-Specific Guidance

<PlatformTabs>

<PlatformTabsFabric>

**Tools:** Data Factory Copy Activity, Dataflows Gen2, On-premises Data Gateway

**Key considerations:**
- Use On-premises Data Gateway for databases behind firewalls
- ADF supports parallel partitioned reads for large tables - partition by ID or date range
- For SQL Server, prefer Change Tracking over CDC tables (simpler, lower overhead)
- Dataflows Gen2 is suitable for small reference tables (< 100K rows)

</PlatformTabsFabric>

<PlatformTabsDatabricks>

**Tools:** Lakeflow Connect, JDBC via Spark, Auto Loader (for database exports to files), Debezium (CDC)

<Callout type="warning">
  **Lakeflow Connect is a New Product** - Database CDC support via Lakeflow Connect is still being expanded. For production CDC pipelines today, use Debezium + Kafka or partner connectors. Evaluate Lakeflow Connect's maturity for your specific database engine before adopting.
</Callout>

**Key considerations:**
- Always use `partitionColumn` + `numPartitions` for tables over 1M rows - single-thread JDBC is extremely slow
- `fetchsize` of 5,000-10,000 reduces round trips significantly
- For CDC, Debezium + Kafka is the proven approach; Lakeflow Connect is adding database CDC support but is still new - verify maturity for your engine
- Use read replicas when available - never point Spark JDBC at a production primary unless volume is small

</PlatformTabsDatabricks>

<PlatformTabsSnowflake>

**Tools:** Snowpipe (file-based), External stages, Partner connectors (Fivetran, Airbyte, HVR)

<Callout type="warning">
  **Snowflake OpenFlow Requires BYOC** - Snowflake's OpenFlow framework is early stage and requires Bring Your Own Connector (BYOC). For database ingestion into Snowflake today, use partner tools (Fivetran, HVR) or self-managed Snowpipe from file exports.
</Callout>

**Key considerations:**
- Snowflake has no native JDBC connector - data must come via files or partner tools
- For CDC, Fivetran or HVR are the standard choices
- Snowpipe auto-ingest is excellent for database-to-file-to-Snowflake patterns
- Use `MATCH_BY_COLUMN_NAME` to handle column ordering differences between exports

</PlatformTabsSnowflake>

</PlatformTabs>

### Database Source Discovery Template

| Discovery Item | Example (PostgreSQL) |
|----------------|---------------------|
| Database engine & version | PostgreSQL 15.4 |
| Hosting | AWS RDS, Azure Database, self-hosted |
| Read replica available? | Yes - use for all extracts |
| CDC possible? | Yes - needs `wal_level = logical` (restart required) |
| DBA available? | Client DBA, 2-week lead time for changes |
| Network access | Private subnet, VPN required |
| Largest table | `orders` - 85M rows, 42GB |
| Schema change frequency | Monthly app deployments, 2-3 column changes per quarter |
| Deletion behaviour | Hard deletes on `users`, soft deletes on `orders` (is_active flag) |
| Time zone | UTC (verify - some databases use local time) |
